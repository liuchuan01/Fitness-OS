# 个人数据分离与新用户冷启动总方案

状态：2026-09-13 已实施并完成代码、迁移与浏览器验证；真实模型写入因缺少 Key 尚未验收。本文保留原方案推导，现行契约以正式专题文档与根 AGENTS.md 路线图为准；证据见 ../engineering/DATA-SEPARATION-VALIDATION.md。

本文保留实施前的仓库检查、用户反馈与设计推导；下文的“现状”“待核对”和建议语气均属于当时的方案背景。实施结果、当前契约与验收限制以正式专题文档、根目录路线图及交付记录为准。

## 1. 目标与已明确的方向

让他人获得代码后，从自己的空白健身数据开始使用；现有用户的真实数据完整保留，可以在独立 Git 仓库中备份；应用升级不覆盖个人数据。

根据用户反馈，本方案采用以下方向：

1. 保留可参考的个人档案、周期和首次计划案例，但案例不能成为正式用户数据。
2. 将 `data/Agent.md` 中的个人训练偏好迁入个人档案，制定或修订计划之前必须读取。
3. 所有个人健身业务数据放入一个独立目录；后台的教练设置、自动任务、模型选择与 API Key 统一归属应用配置层，普通设置合并到 `config/settings.yaml`，Key 继续由 DSH 凭据机制管理；会话与调度运行状态另放 `runtime/`。
4. Agent 入口文档收敛为文档地图，包含资源清单、任务必读路径和少量核心边界；详细规则放到专题文档。
5. 由一个工作区根目录统一推导数据、配置和运行路径，所有读写入口使用同一份路径配置。
6. 沿用现有模型 Key 配置功能，不增加 Key 正确性检查流程，不把连接验证作为建档步骤。调用失败沿用正常错误与重试机制。
7. 冷启动采用简短、分轮的了解过程，允许用户逐步补充信息。

第一阶段以单用户独立工作区为范围。账号、多租户、自动 Git 同步、云备份和完整长期周期规划系统不在本次范围。

临时目录中的隔离验证确认：完全空目录会因缺少肌肉映射失败；只提供两份公共肌肉规则时，数据层可以生成包含 67 个肌肉的空投影，训练记录为零。公共动作库有 31 个动作，无历史时仍能查询肌肉关联动作。放入无效 program 后，现有 `validate all` 仍通过，说明周期校验需要补齐。

### 2.2 现有文档冲突

- 根目录要求真实数据不随功能提交，但个人数据已经被 Git 跟踪。
- `data/README.md` 写着 AI 不直接写入，`data/Agent.md` 和数据架构则允许授权范围内的业务 draft。
- 数据架构描述 program 应经过 schema 校验，当前统一校验器尚未覆盖它。
- 周一测量、固定热身和训练编排等个人习惯出现在通用指引里。

实施时统一到“Agent 在授权范围内提出业务草稿，本地程序完成校验和正式写入”的契约。不能仅移动目录而保留互相矛盾的说明。

## 3. 目标目录与独立 Git 备份

### 3.1 应用仓库

```text
training-app/
  AGENTS.md                         开发 Agent 文档地图（目标名称）
  docs/                             产品、数据、Agent、部署等正式契约
  resources/fitness/
    manifest.yaml                   公共知识与计算规则版本
    muscles/muscle_map.yaml
    muscles/stimulus_rules.yaml
    exercises/                      后续补充器械、别名、替代关系等公共元数据
  templates/fitness/                新建文件的结构模板，不含个人事实
  examples/fitness-starter/         一套完整的虚构使用案例
  dsh-fitness/                      DSH Host 集成、公共教练指令与导航生成
  public/models/                   人体模型和绑定
  shared/                          canonical ID、schema、计算和投影
  tests/fixtures/                  合成测试夹具
```

### 3.2 用户工作区

```text
my-fitness-workspace/               WORKSPACE_ROOT，不要求它是 Git 仓库
  AGENTS.md                         应用生成的训练 Agent 导航入口
  fitness/                          FITNESS_ROOT，可独立 git init / clone
    .git/                           用户自行配置的可选 Git 仓库
    .gitignore                      排除临时文件与自动备份副本
    manifest.yaml                   数据格式、公共规则版本等可迁移信息
    profile.yaml                    身体档案、长期目标、约束、训练偏好
    programs/                       用户确认的周期方向
    plans/YYYY/                     每日具体计划
    workouts/YYYY/                  实际完成记录
    metrics/                        身体指标、有氧、营养等真实记录
    exercises/preferences.yaml      用户动作熟悉程度、偏好与限制（按需创建）
    imports/raw/                    个人原始导入资料
  config/
    settings.yaml                   agent / automation / model 三类普通后台配置
    …                               DSH 凭据存储能否定向至此，实施时核对
  runtime/
    dsh/                            DSH_HOME：官方会话与 Host 状态，凭据落盘见下文
    automation/                     claim、retry、运行记录
    onboarding/                     初始化进度、未提交草稿等可恢复过程数据
```

`fitness/` 是完整的健身业务备份单位。档案、个人计划、周期、指标和原始导入不再分散在代码根目录与其他目录。它可以位于应用仓库外；若开发时放在应用仓库内，其整个工作区应被外层 Git 忽略，避免双重跟踪。

`config/` 与 `runtime/` 不进入健身数据仓库。恢复健身仓库即可找回身体档案与计划；应用设置可单独恢复，凭据可重新配置，聊天历史是否保留取决于是否另行备份 DSH 状态。

后台统一管理与底层统一文件是两件事：目前教练设置、自动任务分别写两个 YAML，API Key 通过 DSH 凭据接口保存或由环境变量提供。目标按“健身数据／应用配置／运行状态”划分，Key 属于应用配置，不因由 DSH 保存就归为运行状态。

普通后台设置合并到 `config/settings.yaml`，设置 `schema_version`，按以下分区管理：

- `agent`：教练语气、回复长短和交互方式；训练偏好仍在个人档案。
- `automation`：每日计划是否启用、执行时间、时区和错过任务的处理策略。
- `model`：模型提供方、模型选择及必要的凭据引用，不保存 Key 原文。

管理后台可以继续分区展示；服务端通过同一配置读写入口做分区校验、合并和原子保存。修改一个分区不得覆盖其他分区，后台并发保存需避免丢失更新。迁移时将原有两个 YAML 的配置合并到新文件，保留原值；合并成功后使用单一来源，不长期双写。配置变化分别通知 DSH 或 Scheduler，不作为健身事实变更刷新 Dashboard。

API Key 继续由现有 DSH 凭据机制或启动环境管理，不引入新的明文 Key YAML，也不为了“放在一起”重复保存 Key。实施时核对已安装 DSH 是否支持把凭据存储定向到 `config/`：支持则统一放在配置目录；不支持则保留其官方存储位置，在部署与备份说明中明确这一物理布局例外。不能预先承诺自定义凭据路径，也不能为迁就目录把整个 DSH 会话库搬入配置目录。`DSH_HOME` 始终位于健身目录外；在尚未确认凭据分离前，不能把其中内容当作可公开、可提交或可随意清理的缓存。

第一阶段只提供独立 Git 仓库兼容性和操作说明，不自动执行 `git init`、commit、push 或配置远端。数据扫描、文件监听和业务审计必须跳过 `.git/`；Git 元数据变化不触发身体数据刷新。Git 恢复后仍要执行业务校验，不能把仓库合并成功当作数据有效。

### 3.3 路径统一

统一路径解析器接收 `WORKSPACE_ROOT`，推导 `FITNESS_ROOT`、`CONFIG_ROOT`、`RUNTIME_ROOT` 与 `DSH_HOME`。应用资源路径由安装位置推导，不依赖 Agent 当前 shell 所在目录。

前端不拼接磁盘路径；Fitness 服务、DSH 交互与自动 Session、CLI、导入脚本、监听器和调度审计共同使用解析结果。CLI 在代码目录或用户工作区执行时应得到一致结果，不能默默回退到另一个 `data/`。

已有 `DATA_ROOT`、`RUNTIME_ROOT` 等配置通过明确的兼容映射过渡；若与新工作区配置冲突，启动时报错并指出冲突路径，禁止静默选择。第一阶段避免允许各业务子目录任意拆散到不同位置。

DSH 的 cwd 指向用户工作区；公共资源和业务契约以启动时生成的准确路径提供。CLI 使用应用安装位置的统一入口，不要求用户工作区拥有 `package.json`。Docker 同样将应用与公共资源只读安装，工作区作为持久化目录挂载。

| 聊天与调度状态                              | `runtime/`                                                        | DSH 与 Scheduler 各自维护          | 否               |
| 模板、案例与测试数据                        | 应用 `templates/`、`examples/`、`tests/fixtures/`                 | 明确区分用途，不自动读入正式数据   | 否               |

公共知识只保留一个维护源。不要把规则复制进每个用户的 Git 仓库再分别修改。数据清单记录依赖版本；公共规则升级需显式校验、迁移或重算，不能使旧结果在应用升级后无说明地变化。

### 4.2 是否在原地保留案例

建议保留案例，但不把可执行案例留在正式扫描位置。现有扫描器递归读取 YAML，仅改名为 `example.yaml` 仍可能被当作业务数据；固定的样例日期也不能作为可靠隔离方式。

采用以下方式兼顾原地可发现性与数据边界：

- 在 `examples/fitness-starter/` 下保持与 `fitness/` 一致的相对结构，提供一份档案、一份周期、一份首次计划，以及可选的对应完成记录和身体测量。
- 案例使用虚构人物、数值和情境。可以复用文件结构与一般规则，不能直接将现有个人数据改名后发布。
- 案例 README 说明各文件关系、哪些内容是事实、哪些内容是计划，以及如何查看和显式导入到独立演示工作区。
- 迁移后在应用 README、资源地图和原 `data/README.md` 保留导航说明，指向案例；原 `profile.yaml` 和活动业务目录不保留可被默认读取的示例 YAML。
- `templates/` 提供无个人事实的结构模板；`examples/` 展示连贯使用过程；`tests/fixtures/` 验证行为。三者都不在新工作区初始化时自动填入真实记录。
- 案例按相同 schema 校验，计划和完成记录的计算字段由程序产生，不手写。示例 ID、关联文件、日期与周期覆盖关系需要一致。

若希望演示带数据的产品，单独创建演示工作区并显式载入案例；普通新用户始终为空白。应用读取失败时也不能回退到演示数据。

## 5. 个人偏好与 Agent 文档地图

### 5.1 偏好迁移

当前 `data/Agent.md` 中以下内容迁入现有用户的 `fitness/profile.yaml`，保留原意并去除与已有档案重复的表达：

- 热身区域、动作数量和选择偏好。
- 主训练动作数量、器械区与自由重量区偏好。
- 主动作递增热身组的编排习惯。
- 默认不安排训练后冷身等个人选择。
- 新动作引入节奏、根据历史重量渐进等个人执行偏好。

公共契约保留单位口径、真实数据优先、未知不猜测、计划与 workout 分开、禁止手写 computed 等要求。周期内的容量目标、进阶和复盘规则放到 program；当天临时请求保留在当日计划意图中，不自动覆盖长期偏好。

区分档案与设置：凡会影响训练内容、器械选择、时间和身体限制的信息进入健身数据；教练语气、回复长短等留在应用设置。相同偏好只有一个正式来源。

### 5.2 保证计划前读取

仅在导航里写“记得读档案”不够。建议组合使用以下机制：

1. 所有计划生成与修订任务都以统一的必读清单开始，交互与自动 Session 使用同一规则。
2. 在 DSH Host 的现有 `systemPrompt.section()` 扩展中按请求读取当前档案，将已确认目标、约束和偏好提供给 Agent；不只在首个 Session 注入一次，不依赖旧聊天记忆。
3. Agent 继续读取目标日期的周期、最近训练和指标、动作资源及已有计划；资料缺失时明确处理，不读案例补齐。
4. 计划提交携带或关联本次使用的档案版本；本地提交前核对版本，避免用户刚修改偏好，旧任务仍提交过期计划。版本校验只能保证上下文未过期，不宣称证明模型理解或遵守了每条偏好。
5. 新工作区没有确认档案时进入建档，自动任务不生成计划；用户明确选择一次性训练时，可确认最小必要信息后生成单次计划。

该扩展负责提供确定的业务上下文，不由 Fitness 服务重新拼装模型计划生成提示词，也不新增第二套模型调用链。

建议必读顺序：个人档案与偏好 → 覆盖目标日期的 program（无则说明）→ 近期真实 workout 与指标 → 公共动作和计算契约 → 目标日期已有 plan。修订时必须读取原计划。

### 5.3 Agent 入口变薄

当前仓库使用根 `AGENT.md` 和 `data/Agent.md`。目标统一采用 `AGENTS.md`，但重命名需同步 DSH 指令发现配置、测试与所有引用，确认新旧入口不会重复注入。此次方案文档不执行重命名。

保留两个职责不同的入口：

| 入口                 | 面向对象                             | 保留内容                                                       |
| -------------------- | ------------------------------------ | -------------------------------------------------------------- |
| 应用根 `AGENTS.md`   | 开发项目的 Agent                     | 文档地图、公共与个人资源归属、少量架构边界、现有唯一项目路线图 |
| 工作区根 `AGENTS.md` | 训练 DSH Agent及处理数据的外部 Agent | 当前健身目录、公共资源路径、按任务必读文档、CLI 入口和写入范围 |

工作区入口由应用模板生成，包含本机解析后的路径，放在个人健身 Git 外。迁移机器或升级应用时可重新生成，不依赖个人数据仓库里的绝对路径。它是导航入口，不是另一份训练事实源，也不包含 API Key。

详细内容继续归入既有专题文档：

| 主题                                   | 权威文档                                                  |
| -------------------------------------- | --------------------------------------------------------- |

## 6. 新用户冷启动

### 6.1 初始化与入口

初始化创建工作区目录、导航和默认应用配置。健身目录只创建必要元数据，不填充年龄、体重、无伤病声明、周期或训练记录。重复初始化不能覆盖已有文件；发现已有档案时进入恢复或迁移流程。

首页保留人体和公共动作探索，中央提供“建立我的训练档案”。已有部分信息时显示继续入口；已有首份计划时显示计划入口。模型 Key 沿用现有设置页，填错时正常调用报错，不新增连接测试、向导步骤或完成状态。

### 6.2 分轮了解与确认

DSH 用对话逐步了解，每轮两三个重点，优先询问会改变第一份计划的内容：

1. 目标和训练经验：想改善什么、近期是否训练、熟悉哪些动作。
2. 现实条件：每周可安排几次、单次时间、场地与器械。
3. 身体情况：用户报告的当前不适或已知限制，以及与任务相关的基础信息。

完整饮食日志、体脂率、详细历史重量等不作为开始的条件。缺失的测量值、RPE 和不适情况保持未知；对影响安排的关键信息补问，不把未回答等同于否认。

然后展示“目前对你的了解”供用户修改和确认，明确分开事实、目标、偏好、未知项和教练建议。确认可在一张摘要卡完成，不要求逐字段审批。

档案记录低频事实与偏好；体重等测量进入 metrics，附实际日期；年龄需要时间依据；短期疲劳不写成永久限制。事实可记录来源类型和确认时间，不复制完整会话正文。

### 6.3 初步安排与首次计划

通常先给出一个短期可调整的训练方向，再生成首次训练日的具体计划。建议将最初一到两周作为观察窗口，实际长度依据用户情况确定，不预置固定分化、训练天数或减脂目标。

program 表达目标、每周方向、约束和复盘条件；plan 表达某天的动作与执行安排。用户确认方向后，本地校验并保存 program，再生成和 finalize 首份 plan。不同步骤可以恢复，不要求把所有文件一次性提交。

如果用户只想今天训练，允许建立最小已确认档案后生成一次性计划，不强迫创建周期。每日自动任务仍要求有效周期。

无历史重量时，计划需要表达现场选择负重和目标用力程度，不根据年龄、性别或体型编造公斤数。计划 schema 应为这类执行指引提供明确字段，实际 workout 只记录用户报告或确认的完成值。当前 plan 大量复用 workout 结构，实施时只扩展必要的处方字段，不让计划指引被复制成实际数据。

### 6.4 首训反馈与后续运行

训练后收集实际完成、调整和关键感受，经校验保存 workout，再用于下一次计划。用户可以确认按计划完成的具体内容；不推测实际 RPE、时长和不适，也不因对话结束自动生成 workout。

每日自动计划默认关闭。用户启用后，Scheduler 先检查确认档案、有效周期和目标文件，再复用既有幂等、重试与文件校验机制。模型配置错误沿用任务失败处理。

不使用单个 `onboarded: true` 决定所有行为：档案确认、有效周期、首次计划、实际训练分别由正式数据判断；未完成步骤和草稿放入 `runtime/onboarding/`。删除 runtime 后仍能根据正式文件恢复基本进度，聊天历史不是档案存在的前提。

## 7. 数据与运行保障

### 7.1 校验与提交

为 profile、program 和本轮实际写入的指标补齐 schema。分别区分允许缺失的草稿字段与提交所需字段，避免结构模板被误当作完整档案。

建档可以写档案、已确认指标和 program；生成计划可以写目标 plan；记录实际训练必须依据用户明确事实。自动任务的写入范围仍只允许目标日期计划及必要临时文件。

完整审计覆盖健身业务文件，排除 `.git` 等非业务元数据。配置和公共资源通过独立权限保护及适用的审计规则限制，不能因为移出健身目录而默认允许 Agent 修改。目录隔离和提示词不等于操作系统沙箱；容器只读挂载等实际保护需按部署验证。

未提交草稿放在运行目录，避免半成品进入正式扫描导致整个 Dashboard 无效。正式写入经过 schema、必要计算、冲突检查和原子保存。跨档案、周期与计划的提交按步骤记录并可重试，不把单文件原子 rename 宣称为跨文件事务。

### 7.2 未知值和空态

- 没有历史不表示恢复良好，空投影不返回有健康含义的恢复百分比。
- 缺少体重或实际负重导致无法计算时，表达估算缺失；仍可显示涉及肌肉、记录组数等可确定信息。
- 公共计算默认参数属于算法假设，不回填为真实 RPE 或身体数据。
- 无计划、无 workout、无可用估算和服务读取错误分别表达。
- 无历史时公共动作可供探索，但公共肌肉关系不等于个人适用性或熟练程度。

### 7.3 迁移、恢复与发布

先生成原数据清单和备份，在隔离副本迁移档案、偏好、周期、计划、实际记录及原始导入；验证引用、日期、计算和统计后再切换工作区。旧数据保留到验证结束，不通过清空原目录启动迁移。

本次数据分离应尽量保持原计算规则版本，避免目录迁移与算法调整同时改变历史值。旧 plan/workout 的相对文件引用需要随目录变化校验或改写。

现有用户的应用配置和 DSH 状态另行迁移。保留聊天时需要验证工作区路径变化后的 Session 归属，不假定复制 DSH_HOME 就能完成恢复；新用户必须使用新的 DSH_HOME，不能借用旧 Session 和调度游标。

镜像只包含应用、公共资源、模板与案例，不包含个人数据；默认启动读取用户挂载的工作区。截图、文档示例和发布附件也要检查个人数据。

当前 Git 删除文件和新增忽略规则不会删除历史记录。对外提供完整 Git 仓库前，需要另行决定清理历史或从审查后的干净快照建立发布仓库；该决定不在本次写方案时执行。

## 8. 建议实施拆分与验收

本节是待评审方案的实施拆分，不改变根目录唯一项目路线图的优先级。通过评审后，再将接受的阶段纳入根目录路线图。

| 阶段                 | 主要交付                                                   | 验收要求                                                                 |
| -------------------- | ---------------------------------------------------------- | ------------------------------------------------------------------------ |
| A：数据分离基础      | 统一路径、公共资源、独立健身目录、外部配置、迁移和部署调整 | 全新工作区无个人数据；旧工作区迁移前后记录与统计一致；各入口读写同一目录 |
| B：案例和 Agent 导航 | 虚构连贯案例、结构模板、薄入口、偏好迁移与请求上下文       | 案例不被正式扫描；交互与自动计划均获得当前档案；改偏好后下一次请求生效   |
| C：建档和首份计划    | 分轮问答、确认、schema、初步周期与计划、恢复机制           | 重启可继续；失败不丢已确认档案；重复提交不覆盖已有业务结果               |
| D：首训与自动化接续  | 实际完成反馈、空态与未知值处理、自动任务前置条件           | plan 不自动变 workout；无数据不显示假恢复；自动任务默认关闭且不越界      |

重点验收场景：

1. 同一应用分别启动两个工作区，档案、计划、配置、会话和调度状态不串用；第一阶段可以逐个启动，不要求并发多租户。
2. 从代码目录和工作区执行 CLI，目标一致；错误或冲突路径明确失败。
3. 只有公共资源和空健身目录时，人体与动作探索可用，不载入案例。
4. 独立健身 Git 仓库提交、恢复、切换分支后可重新校验；`.git` 修改不触发业务刷新。
5. 无档案、部分档案、已确认档案、已有 program、已有计划无训练、已有真实训练分别呈现正确入口。
6. 用户修改个人偏好后，新会话和自动任务均使用新内容；旧任务提交时能发现档案版本变化。
7. 模型调用中断、草稿无效、计划文件已存在时，可重试且不重复创建、不覆盖事实。
8. 错误 Key 沿用现有调用错误，不增加连接检查流程，不重置已保存档案。
9. Docker 重建后个人档案仍可写且保留，镜像不含原用户数据；只恢复健身 Git 也能重新接入应用。
10. schema、聚焦集成与实际 DSH Host 验证分别记录；代码检查通过不替代真实 Agent 读取、写入和恢复验证。
11. 原教练设置和自动任务配置迁入同一 `config/settings.yaml` 后行为保持一致；各分区保存不覆盖其他配置，模型 Key 无重复存储。验证 DSH 的实际凭据路径并记录；健身 Git 备份不包含后台配置或 Key。

## 9. 本轮评审重点

以下是本方案给出的具体建议，评审可以直接对条目提出修改：

1. 使用工作区下 `fitness/`、`config/`、`runtime/` 三分结构，`fitness/` 独立配置 Git；普通后台设置合并到 `config/settings.yaml`，Key 同属应用配置层、继续由 DSH 管理。
2. 保留一套虚构连贯案例到 `examples/fitness-starter/`，原位置只留导航，不留活动 YAML 示例。
3. 将个人训练偏好统一迁入档案，并通过 DSH 按请求提供当前档案，配合提交时版本核对。
4. Agent 文档保留应用与工作区两个薄入口；详细契约归入现有专题文档，实施时统一文件名与发现机制。
5. 冷启动使用分轮对话、摘要确认、短期初步安排与首份计划，允许一次性训练和中途恢复。

本轮已按后续用户授权实施；不自动初始化个人 Git、不清理历史、不推送发布。实现及验证证据由当前交付记录提供。
